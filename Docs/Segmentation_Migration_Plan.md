# План миграции пяти вкладок сегментации на общие компоненты

[Фактический аудит и дефекты](Segmentation_Tabs_Audit.md) · [Документация](README.md)

План составлен по `89c9c11`, ветка work. Порядок: сначала восстановить нарушенные
контракты и зафиксировать поведение, затем переносить общий I/O и экспорт,
после этого представление/морфологию и алгоритмические адаптеры.
Документ не является отчётом о выполненной миграции. Все этапы реализации ниже
ещё предстоят; выполнено исследование исходников и описанные в аудите пробы.

## 1. Цель и границы

Вкладки threshold, gradient, interactive, traditional_ml и deep_learning должны:

- использовать общие файловые, геометрические и масочные службы из utils_new;
- использовать повторно общие Qt-компоненты из ui, сохраняя отдельные параметры
  и алгоритмы каждого метода;
- сохранять формат пресетов, результаты и пользовательские файлы там, где
  поведение переносится без намеренного исправления ошибки;
- явно документировать исправления, меняющие результат: dtype/resize, неоднозначный
  Segment, физическая OBB, классы масок и старая относительная морфология;
- работать отдельно и в main, с правильным попаданием мыши и без регрессии DLL
  PyTorch на Windows; не менять dependency-профили CUDA/OpenCV в этой миграции.

Переносом общих функций **не является** создание общего набора изображений на
все вкладки: сессии и пользовательские параметры остаются независимыми.
Также сюда не входит реализация незавершённых SAM/SegFormer, переписывание
сетей, обучение новых моделей или массовое удаление utils для других вкладок.

## 2. Принципы архитектуры

1. Композиция из небольших служб и Qt-controller, а не огромный BaseWindow с
   условием для каждого алгоритма и десятками скрытых обязательных атрибутов.
2. Направление зависимостей: tabs/ui → utils_new; вычислительное ядро не импортирует
   QWidget, QMessageBox, matplotlib backend, настройки приложения или main.
3. ui_tabs оставляет сборку специфичных layouts. Общие виджеты/контроллеры принадлежат ui.
4. Один владелец каждого алгоритма. Старые импорты временно делегируют новому
   владельцу; параллельно поддерживаемых копий функции не оставлять.
5. На первом шаге сохранить legacy tuple на границе существующего UI. Новое
   геометрическое ядро использует Annotation/ImageSize в пикселях; преобразования
   идут через уже существующие from_legacy/to_legacy и явный размер.
6. Реальный пользовательский клик проверяется через QWindow и widgetAt.
   Проверка вызова метода или clicked сама по себе не ловит перекрытия интерфейса.
7. Один этап — один проверяемый коммит/небольшая группа коммитов в work. После
   успешной проверки обновлять журнал плана и публиковать ветку. Не переписывать историю.

## 3. Целевое распределение ответственности

Ниже предлагаемые имена новых файлов, а не список уже существующих компонентов.
Создавать файл только при наличии вынесенной ответственности; не добавлять пустой
framework заранее. Существующие имена публичных API сохранять через адаптеры.

```text
utils_new/
  dataset_files_new.py         # владелец чтения файлов, размеров и LazyImageCache
  dataset_yolo_labels_new.py   # владелец YOLO parser/writer и LabelSavePlan
  annotation_processing.py    # уже готовое mask -> Detect/OBB/Segment
  annotations/                # уже готовая физическая геометрия/типы
  morphology.py               # уже готовые операции над массивами
  threshold_processing.py     # уже готовые пороговые алгоритмы
  presets_store.py            # новое: JSON/schema/legacy migration без окна
  settings_store.py           # новое, поздний этап: данные и валидация общих настроек
  segmentation/
    models.py                 # ImageFrame, маски, спецификации, результаты
    image_session.py          # список путей, текущий кадр, политика загрузки и cache
    postprocessing.py         # проверяемые общие стадии, без чтения виджетов
    export.py                 # выбор объектов/план/запись через YOLO writer
    backends/
      gradient.py             # перенос математики из gradient_ops без её изменения
      interactive.py          # перенос interactive_ops с сохранением ROI/markers API
      traditional_ml.py       # признаки/train/predict и metadata schema
      deep_learning.py        # адаптеры моделей; фактический импорт backend по запросу
ui/
  image_navigation.py         # существующий виджет, не дублировать
  log_widget.py               # существующий виджет
  morphology_ui.py            # существующий MorphologyWidget
  interactive_params_ui.py    # существующая специализированная панель
  DL_predict_settings.py      # существующие специализированные панели
  image_conversion.py         # канонический numpy_to_qpixmap
  image_view.py               # существующий SmartGraphicsViewNew переносится сюда
  annotation_review_view.py   # существующий DatasetReviewGraphicsView переносится сюда
  settings_service.py         # поздний этап: единственный QObject settings + сигналы
  segmentation/
    image_input.py            # dialogs/progress/navigation binding к ImageSession
    result_views.py           # набор стадий и overlay; 4 или 6 панелей по конфигурации
    histogram.py              # FigureCanvas + update(gray, threshold)
    object_list.py            # чекбоксы/фокус/координаты результатов
    preset_panel.py           # выбор/сохранение/удаление и binding параметров
    session_controller.py     # Qt orchestration и debounce, не вычислительная математика
    jobs.py                   # поздний этап: workers/signals/cancellation
```

`utils_new.smart_view_new` и `dataset_review_view` содержат Qt, несмотря на путь.
Правильнее перенести их реализацию в ui и оставить прежние модули совместимыми
реэкспортами/алиасами. Сначала переиспользовать работающий код, не писать ещё один
просмотрщик. Их перенос не должен ломать редактор/просмотр датасетов и monkeypatch
существующих потребителей. Для фасада явно проверить identity публичных классов.

`utils_ops.gradient_ops`, `interactive_ops`, `traditional_ml_ops`, `deep_learning_ops`
после соответствующего этапа станут адаптерами к единственным владельцам в
utils_new/segmentation/backends. `utils_ops.segmentation_ops` остаётся совместимым
API для остальных вкладок, но новые пять больше не импортируют его смесь UI и math.
Не переносить все четыре backend одним большим коммитом.

## 4. Контракты, которые нужно зафиксировать до переноса

### 4.1. Изображение и сессия

ImageFrame содержит path, идентификатор/revision, исходный ImageSize, рабочий
ImageSize, BGR uint8 для алгоритмов, grayscale, фактические sx/sy и политику
нормализации/resize. Полноразмерные пиксели необязательно хранить постоянно:
нужны исходный размер и воспроизводимый способ чтения, а не второй eager-кэш.

ImageSession хранит пути, current_index, get(index), смену загрузки, ошибки и
shutdown. Каждый экземпляр принадлежит одной вкладке. Отдельно задаётся,
нужны ли обучающие annotations: ML нужны, остальные обработчики кадра сейчас
читают image/gray. Проверить автоподбор перед отключением ненужного чтения TXT.

Сначала сохранить ограничения 1024 для четырёх вкладок и 640 для ML. Изменение
разрешения ML меняет признаки и модель, это отдельное изменение, а не общий default.
Для первого compatibility-прохода выбрать `legacy-segmentation-v1` для
преобразования яркостей и `floor_nonzero` для resize: сохранить прежние значения
на обычных снимках, но ограничить каждую размерность снизу одним пикселем.
Существующие dataset-вкладки продолжают использовать свой min-max/round путь.
Политики входят в ImageFrame и metadata/preset, а не определяются по имени вкладки.
Переход конкретного метода на min-max/round делается отдельным явным изменением
с ожидаемыми новыми масками, а не побочным эффектом замены import.

### 4.2. Маски и стадии

Различать минимум BinaryMask (uint8 0/255), LabelMask (целые class IDs) и
визуальную/вероятностную карту. Указывать image_id/revision и рабочий размер.
Отсутствие результата — не то же, что валидная пустая маска.

Для прежней бинарной обработки class_id=0/union остаётся явным совместимым
режимом. Исходные class IDs модели не уничтожать ради показа. Морфологию
применять к выбранной бинарной маске или по классам с явным правилом конфликтов,
а не к числовому порядку индексов. Class-aware режим приёмки отделить от переноса.

Порядок каждой цепочки сохранить отдельно:

- threshold: бинаризация → исходная bitwise-инверсия → morphology → пользовательская
  инверсия → извлечение объектов;
- gradient: инверсия gray → градиент → threshold → morphology → удаление мелких
  контуров → optional fill + дополнительный closing → пользовательская инверсия;
- interactive: алгоритм с ROI/FG/BG → mask → morphology → инверсия → объекты;
- ML: признаки/модель или выбранный кластер → mask → morphology → инверсия;
- DL: preprocess/predict/postprocess модели → mask → morphology → инверсия.

Не сливать эту разную семантику в один набор boolean-флагов общей функции.

### 4.3. Геометрия, выделение и экспорт

Нормализованные tuples UI не смешивать с pixel-edge Annotation. Размеры задаются
в порядке ImageSize(width,height), ndarray — (height,width). OBB вычислять в
физических пикселях, а не на нормализованной прямоугольной картинке.

Checked-объекты для экспорта, focused-объект инспектора и local index в
отфильтрованном overlay — отдельные состояния. На каждый результат назначать
revision; не сохранять старые индексы для нового множества контуров. Исходное
поведение «после пересчёта все объекты отмечены» сохранить как initial policy;
улучшенное сохранение выбора — отдельное изменение с правилом сопоставления.

Общий export-service получает annotations, selection, frame/размер и destination.
Он использует готовые build_label_save_plan/format_label_save_confirmation и
новый writer. Qt-dialog находится в ui. Пустой TXT допустим, но число выбранных
объектов и замена существующего файла должны быть понятны пользователю.
Для этих пяти вкладок текущий путь остаётся рядом со снимком; правила canonical
labels/split из YAML-редактора не переносить туда без отдельной поддержки YAML.

### 4.4. Морфология и пресеты

Хранить operations/order/shape/kernel_px/iterations, а не скрытые Qt sliders.
Legacy presets относительные: kernel = max(1,int(factor*min(H,W))). У gradient
slider→factor делится на 200, у interactive/ML/DL на 100. Это часть мигратора.

Версионировать состояние: legacy relative — разрешать относительно текущего
рабочего кадра; новые pixel-настройки — фиксированные px. Не конвертировать
старый preset по первому изображению навсегда, если набор имеет разные размеры.
При сохранении новой схемы явно записывать систему единиц и версию.

Автоподбор обязан сохранять/восстанавливать полный morphology.get_settings и
все параметры применённого метода, индекс кадра, выделение и флаги. Использовать
try/finally и восстановление прежнего signalsBlocked, не безусловный blockSignals(False).

  random_state, scaler, классов, superpixels и joblib metadata.
- [ ] В train-data заменить загрузку старых annotations новым parser через
  адаптер размеров/форматов; не смешивать pixel Annotation и legacy tuples.
- [ ] Сессию сделать ленивой; для обучения явно собирать нужные samples/features,

Приёмка: K-Means/MeanShift, минимум одна supervised-модель, superpixel-путь,

### Этап 8. Deep Learning и фоновые jobs — L

- [ ] Ввести typed результат с raw class/probability data и отдельным preview.

- [ ] Request содержит image_id, revision, model_revision, параметры; устаревший

  используется конкурентно без явной гарантии backend.
- [ ] Cancel между стадиями; для неотменяемого native вызова не обещать мгновенную

- [ ] Закрытие вкладки/программы учитывает активный job; не уничтожать работающий

Приёмка: stub segmentor в CI, ошибка/нет DLL/нет optional backend, resize roundtrip,

## 7. Рекомендуемая первая поставка

Начать с этапа 0 и общего I/O/экспорта для threshold и gradient (этапы 1–2).
Это небольшой вертикальный проход через существующие новые утилиты с высоким
повторным использованием. Он закрывает уже сломанный автоподбор и форматы,
не затрагивая сразу ROI, train-data ML и metadata нейросетей. Далее UI/морфология,
interactive, ML, DL/jobs и транзитивная очистка настроек — в указанном порядке.
